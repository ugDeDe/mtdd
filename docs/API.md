## Подключение и токены

```
              control_host:control_port (127.0.0.1:9090)
 admin ─────►  /v1/*  (все маршруты)
 read  ─────►  /v1/*  (только GET, без ссылок и /metrics)

              metrics_host:metrics_port (127.0.0.1:9091)
 metrics ───►  /metrics  (только он; /v1/* здесь — 404)
```

| Токен | Переменная окружения (имя задаёт конфиг) | Что разрешено |
| --- | --- | --- |
| admin | `api_token_env` | Всё на API-порту, включая изменения и `/metrics` (устарело, см. ниже) |
| read | `api_read_token_env` | Только `GET`; запрещены `/v1/users/{name}/links` (в ссылке секрет) и `/metrics` |
| metrics | `metrics_token_env` | Только `GET /metrics` на порту метрик |

Токены передаются заголовком `Authorization: Bearer TOKEN` и сравниваются за
постоянное время. Неверный токен — `401` с `WWW-Authenticate`, недостаточная
область — `403 forbidden_scope`.

- `control_allow` / `metrics_allow` — списки сетей (`10.0.0.0/8`, `::1`);
  пустой список пускает всех, иначе чужой адрес получает `403`.
- `metrics_port: 0` выключает отдельный слушатель. Непетлевой `metrics_host`
  без токена и без явного `metrics_allow` — ошибка конфигурации.
- `/metrics` на API-порту оставлен для совместимости, отвечает с
  `Deprecation: true` и принимает только admin-токен.
- Частота запросов ограничена на источник и глобально; превышение — `429` с
  `Retry-After: 1`.

Не публикуйте API в недоверенную сеть: это обычный HTTP без TLS.

## Формат ответа

Каждый JSON-ответ — объект с конвертом:

```json
{"ok": true, "request_id": 41, "data": { ... }}
{"ok": false, "request_id": 42, "error": {"type": "not_found", "message": "user not found"}}
```

- `request_id` растёт монотонно в пределах процесса и дублируется в заголовке
  `X-Request-Id`; он же записывается в [журнал событий](#журнал-событий).
- Все ответы — `Cache-Control: no-store`.
- Ответы о пользователе несут `ETag: "REVISION"`. Изменения принимают
  `If-Match: "REVISION"`; устаревшая ревизия — `412 revision_conflict`.
- `202` означает, что изменение записано, но рантайм ещё не подтвердил
  применение.
- Время — RFC 3339 в UTC (`2030-01-01T00:00:00Z`). На вход принимается `Z` или
  смещение `±HH:MM`; дробные секунды отбрасываются.

## Ошибки

| HTTP | `error.type` | Когда |
| --- | --- | --- |
| 400 | `invalid_json`, `invalid_request`, `invalid_field`, `unknown_field`, `invalid_name`, `invalid_query` | Неверное тело, поле или строка запроса |
| 401 | `unauthorized` | Нет или неверный токен |
| 403 | `forbidden`, `forbidden_scope` | Адрес вне allowlist или недостаточная область токена |
| 404 | `not_found` | Нет маршрута или пользователя |
| 405 | `method_not_allowed` | Метод не поддерживается маршрутом |
| 409 | `duplicate_name`, `duplicate_secret` | Конфликт при создании |
| 412 | `revision_conflict` | `If-Match` не совпал |
| 413 | `body_too_large` | Тело больше лимита |
| 429 | `rate_limited` | Превышена частота запросов |
| 500 | `io_error` | Ошибка записи состояния |
| 503 | `overloaded` и др. | Перегрузка; для `/links` — не задан `public_host` |

Неизвестные параметры строки запроса, их повторы и значения вне диапазона —
всегда `400 invalid_query`: опечатка не должна молча менять выборку.

## Маршруты

| Метод и путь | Область | Назначение |
| --- | --- | --- |
| `GET /v1/health` | read | Процесс API жив |
| `GET /v1/ready` | read | Есть включённый пользователь и готов ME |
| `GET /v1/status` | read | Сводные счётчики и пулы ME |
| `GET /v1/system/info` | read | Версия, uptime, `started_at`, pid, потоки, ревизия, профиль безопасности |
| `GET /v1/config` | read | Действующая конфигурация без секретов |
| `GET /v1/ad-tag` | read | Временная подмена рекламного тега: `override` и текущий тег подмены |
| `POST /v1/ad-tag` | admin | `{"ad_tag":"<32 hex>"}` — подменить тег на лету |
| `DELETE /v1/ad-tag` | admin | Вернуть тег из конфигурации |
| `GET /v1/shaping` | read | Правила шейпинга медиа, их источник и живые счётчики (см. [Шейпинг медиа](#шейпинг-медиа)) |
| `PATCH /v1/shaping` | admin | Временно изменить правила шейпинга |
| `DELETE /v1/shaping` | admin | Вернуть правила шейпинга из конфигурации |
| `GET /v1/stats/summary` | read | Пользователи, соединения, трафик, уникальные IP |
| `GET /v1/stats/me` | read | Пулы Middle-End по DC |
| `GET /v1/stats/users` | read | Пользователи, отсортированные по нагрузке |
| `GET /v1/events` | read | Журнал изменений |
| `GET /v1/ja4` | read | Отпечатки JA4 клиентских ClientHello по исходам (см. ниже) |
| `GET /v1/users` | read | Список пользователей |
| `POST /v1/users` | admin | Создать пользователя |
| `GET /v1/users/{name}` | read | Пользователь со статистикой |
| `PATCH /v1/users/{name}` | admin | Изменить поля |
| `DELETE /v1/users/{name}` | admin | Удалить и отозвать сессии |
| `GET /v1/users/{name}/links` | admin | Ссылки `https://t.me/proxy` и `tg://` |
| `POST /v1/users/{name}/rotate-secret` | admin | Новый секрет, старые сессии отзываются |
| `POST /v1/users/{name}/enable` | admin | Включить |
| `POST /v1/users/{name}/disable` | admin | Выключить и отозвать сессии |
| `POST /v1/users/{name}/reset-quota` | admin | Обнулить счётчик квоты трафика |
| `GET /metrics` | metrics | Prometheus (порт метрик) |

`enable`, `disable` и `reset-quota` принимают пустое тело (или `{}`) и
`If-Match`. Повторное действие без изменений не двигает ревизию. Расход квоты
хранится вне `users.json`, поэтому `reset-quota` ревизию не меняет никогда;
`If-Match` сверяется с текущей ревизией.

`/v1/config` и `/v1/system/info` не содержат токенов, секретов и `ad_tag`
(вместо него — `ad_tag_set`). `security` в `/v1/system/info` показывает, на
петлевом ли адресе API и метрики, заданы ли read- и metrics-токены, размер
allowlist, включены ли маскировка и FakeTLS, глобальные лимиты.

### Параметры списков

| Маршрут | Параметры |
| --- | --- |
| `GET /v1/users` | `limit` 1..10000 (по умолчанию все), `offset`, `enabled=true\|false`. Ответ: `users`, `total`, `offset`, `limit` (`null`, если не задан) |
| `GET /v1/stats/users` | `sort=traffic\|connections\|unique_ips\|name` (по умолчанию `traffic`; `unique_ips` — по seen), `limit` 1..1000 (50), `offset`. Ответ: `users` (с `quota_used_bytes` и `data_quota_bytes`), `total` |
| `GET /v1/events` | `after=ID`, `limit` 1..256 (50). Ответ: `events`, `next_after`, `oldest_id`, `capacity` |

## Подозрительные адреса

`GET /v1/suspects` (доступен read-токену) — таблица подозреваемых из
рантайма. Параметры: `sort=matches` (по умолчанию: число разных признаков,
затем счёт) `| score | hits | last_seen`, `min_matches` 0..9, `min_score`
0..100, `limit` 1..100000 (100), `offset`, `format=json|ips` (`ips` — текст,
адрес на строку, для наборов файрвола).

Ответ: `total`, `filtered`, `by_matches` (сколько адресов с 1, 2, … совпадениями),
`watched`, `shadow_banned` и `suspects[]`: `ip`, `matches`, `score`,
`signals` (`{"probe_session": 2, ...}`), `hits`, `first_seen`, `last_seen`,
`visits`, `user`, `sni`, `ja4` (JA4 последнего записанного ClientHello с
адреса или `null`), `platform`, `tls`, `syn` (`ttl`, `window`, `mss`,
`wscale`, `layout`), `watched`, `shadow_banned`, `real_client` (с адреса были и
настоящие сессии: неоднозначные признаки A, E, F, G, H не дают очков). Признаки и веса описаны в
README («Подозрительные адреса и fraud score»).

Поле политики `canary` (bool): пользователь-ловушка, каждое его подключение
записывается как признак `canary`. Ставить только на секрет, который не
выдаётся людям.

Признак `probe_session` рассчитан на аудиторию, которая авторизуется только на
DC2: он срабатывает лишь на незавершённый обмен ключами с DC1. Для аудитории с
другим домашним DC его вес стоит снизить.

## Отпечатки JA4

`GET /v1/ja4` (доступен read-токену, как и остальные GET) — какие
TLS-клиенты (отпечаток [JA4](https://github.com/FoxIO-LLC/ja4), вариант TCP)
проходят проверку секрета, а какие нет. Таблица общая на процесс и
ограничена 256 отпечатками; сортировка — по `total`, затем по `last_seen`.
Параметр: `limit` 1..100000 (по умолчанию 256).

```json
{"ok": true, "data": {
  "capacity": 256, "total": 2, "evictions": 0, "unsampled": 0,
  "sample_failed_per_second": 200,
  "fingerprints": [
    {"ja4": "t13d1516h2_8daaf6152771_e5627efa2ab1", "total": 4,
     "authenticated": 3, "unauthenticated": 0, "throttled": 0,
     "replay": 1, "clock_skew": 0,
     "first_seen": "2030-01-01T00:00:00Z", "last_seen": "2030-01-01T00:00:01Z"}]}}
```

Исходы: `authenticated` — верный секрет, не повтор; `unauthenticated` —
ни один ключ не подошёл, чужой или пустой SNI, теневой бан (уходит в
маскировку или закрывается); `throttled` — то же с адреса, превысившего порог
неудачных проб; `replay` — верный секрет, но ClientHello уже был; `clock_skew`
— верный секрет, часы клиента вне окна.

Ограничения: при заполнении новый отпечаток вытесняет запись с наименьшим
`total`, среди равных — давнее всех виденную (`evictions`). Неудачные исходы
(`unauthenticated`, `throttled`) сканер может слать с любой скоростью, поэтому
отпечаток снимается не более чем у 200 таких ClientHello в секунду на весь
процесс; остальные только считаются в `unsampled`. Успешные, `replay` и
`clock_skew` (уже стоили HMAC) записываются всегда. Prometheus получает только
агрегаты без меток JA4: `mtdd_ja4_fingerprints`, `mtdd_ja4_evictions_total`,
`mtdd_ja4_unsampled_total`.

## Пользователи и политика

```json
POST /v1/users
{
  "name": "alice",
  "max_connections": 8,
  "expires_at": "2030-01-01T00:00:00Z",
  "data_quota_bytes": 10737418240,
  "max_unique_ips": 3,
  "max_devices": 2,
  "rate_limit_up_bytes_per_sec": 1048576,
  "rate_limit_down_bytes_per_sec": 4194304,
  "media_rate_limit_down_bytes_per_sec": 1048576,
  "note": "семья · ноутбук"
}
```

| Поле | Тип | Ограничения | Действие при нарушении |
| --- | --- | --- | --- |
| `expires_at` | RFC 3339 \| null | ≥ 1970 | Новые подключения — `user_expired`, активные закрываются |
| `data_quota_bytes` | целое \| null | ≥ 1 | После исчерпания: новые подключения — `user_quota_exceeded`, активные закрываются |
| `max_unique_ips` | целое \| null | 1..2³²−1 | Подключение с нового IP сверх лимита — `user_ip_limit`; уже известный IP пускается всегда |
| `max_devices` | целое \| null | 1..1000000 | Соединение с новым устройством (`auth_key_id`) сверх лимита закрывается, причина закрытия `device_limit` |
| `rate_limit_up_bytes_per_sec` | целое \| null | ≥ 1024 | Чтение от клиента приостанавливается, пока ведро не наполнится |
| `rate_limit_down_bytes_per_sec` | целое \| null | ≥ 1024 | То же для ответа Telegram (на ME-маршруте — приближённо, см. ниже) |
| `media_rate_limit_up_bytes_per_sec` | целое \| null | 0 или ≥ 1024 | Личный медиа-лимит выгрузок вместо `user_kbps` правила `shaping.media_upload`: `null` — как в правиле, `0` — без личного медиа-лимита |
| `media_rate_limit_down_bytes_per_sec` | целое \| null | 0 или ≥ 1024 | То же для загрузок (`shaping.media_download`) |

`max_connections` сверх лимита теперь отклоняется с причиной
`user_connection_limit` (раньше — общий `overload`). Причины видны в
`mtdd_connections_rejected_total{reason=...}`.
| `tls_domain` | строка \| null | DNS-имя в нижнем регистре, ≤ 253 байт; `""`/`null` снимает | Персональный FakeTLS-домен пользователя (см. ниже) |
| `ad_tag` | строка \| null | 32 шестнадцатеричных символа, не все нули; `""`/`null` снимает | Персональный рекламный тег пользователя (см. ниже) |
| `note` | строка | ≤ 256 байт UTF-8, без управляющих символов | — |

В `PATCH` поле со значением `null` снимает ограничение, `note: ""` очищает
заметку; отсутствующее поле не меняется. Пустой `PATCH` — `400`.

### Персональный SNI (`tls_domain`)

Как в telemt, у пользователя может быть свой FakeTLS-домен вместо глобального
`tls_domain`:

- ссылка `/v1/users/{name}/links` строится с персональным доменом;
- ClientHello пользователя с персональным доменом принимается **только** с этим
  SNI (глобальный SNI для него — отказ), остальные пользователи — только с
  глобальным;
- маскировка пробует реальный сайт любого настроенного домена, глобального или
  персонального: проба с SNI, принадлежащим домену (сам домен или поддомен),
  уходит на этот SNI, остальное — на глобальный `tls_domain`;
- значение приводится к нижнему регистру; неверное имя — `400 invalid_field`;
- хранится в `users.json` (версия `2`), применяется к новым рукопожатиям сразу,
  без рестарта.

### Персональный рекламный тег (`ad_tag`)

Пользователю можно задать свой рекламный тег вместо глобального `ad_tag`:

- в каждом `RPC_PROXY_REQ` этого пользователя на ME уходит его тег, поэтому
  Telegram показывает ему спонсорский канал, зарегистрированный для этого тега;
- остальные пользователи и пользователи без тега идут с глобальным тегом (или
  с подменой из `/v1/ad-tag`, если она задана);
- маршрут Direct (`direct_fallback_dcs`) рекламного тега не передаёт вовсе;
- значение приводится к нижнему регистру; неверный тег — `400 invalid_field`;
- хранится в `users.json` (версия `2`), применяется сразу и к открытым
  сессиям — со следующего запроса, без рестарта.

### Как применяются ограничения

- **Срок и квота** проверяются при рукопожатии и раз в секунду для активных
  сессий. Сессия может превысить квоту на объём трафика за эту секунду.
- **Квота** считает полезную нагрузку в обе стороны (`stats.quota_used_bytes`);
  `stats.quota_reset_at` — время последнего сброса или `null`.
- **Скорость** — лимит задаётся на пользователя и направление и делится
  между его **активными** соединениями (передававшими данные за последнюю
  секунду или стоящими на паузе по лимиту). Деление с перераспределением:
  соединения, упиравшиеся в свою долю за последнюю секунду, делят то, что
  оставили остальные, но не получают меньше равной доли. Одно активное
  скачивание рядом с почти пустыми соединениями получает почти весь лимит.
  У каждого соединения своё GCRA-ведро на свою долю с запасом
  `max(доля, 64 KiB)`, без общей очереди. Новое активное соединение сразу
  получает долю, остальные пересчитываются в течение секунды. Данные не
  отбрасываются и не буферизуются сверх обычного: у источника снимается
  `EPOLLIN`. `PATCH` лимита действует на уже открытые сессии.
- **Медиа** (signed DC −1…−5: загрузки и выгрузки файлов, фото, видео)
  дополнительно ограничивается правилами `shaping` конфигурации: отдельно
  загрузки (`media_download`) и выгрузки (`media_upload`), на пользователя и
  на весь сервер, с выбором DC и запасом на всплеск. Общий лимит сначала
  делится между пользователями, потом между соединениями. Личные
  `media_rate_limit_*` заменяют лимит правила на пользователя. Правила
  меняются через `systemctl reload mtdd` или [`/v1/shaping`](#шейпинг-медиа);
  подробно — в [CONFIG.md](CONFIG.md#шейпинг-медиа).
- **Устройства** считаются по `auth_key_id` — первым 8 байтам зашифрованного
  MTProto-сообщения, которые идут открытым текстом. Одна установка Telegram
  держит один текущий ключ на DC, поэтому число устройств — максимум по DC
  (signed: медиа-DC считаются отдельно, у Android там свой временный ключ).
  Смотрятся только первые 16 сообщений соединения, сообщения обмена ключами
  (`auth_key_id = 0`) пропускаются. Место занимает только ключ с открытыми
  соединениями. Новый ключ сверх `max_devices` вытесняет самый давний ключ без
  соединений (устройство отключилось или сменило временный ключ); если таких
  нет, соединение закрывается при первом сообщении
  (`mtdd_relay_closes_total{reason="device_limit"}`). Ключ с открытым
  соединением пускается всегда. Ключ без соединений ещё
  `device_window_seconds` (по умолчанию 900, 60..86400) остаётся в счётчике
  устройств, но никого не блокирует. Подключённые сейчас —
  `stats.devices_connected` и `mtdd_user_devices_connected{user}`; вместе с
  недавно отключившимися — `stats.devices` и `mtdd_user_devices{user}`.
  Таблица общая для воркеров и обнуляется при перезапуске. Это не
  криптографическая привязка: клиент с одним ключом на нескольких устройствах
  будет считаться одним.
- **Список ключей** — `GET /v1/users/{name}/devices` (доступен read-токену):
  `devices_connected`, `devices` и `keys[]` с полями `id` (короткая метка,
  производная от `auth_key_id`, не сам ключ), `dc`, `connections`,
  `connected`, `idle_seconds`, `ip` последнего подключения и `platform`.
  Одно устройство даёт по ключу на каждый DC, с которым работает.
- **Платформа** определяется грубо, по SYN (`TCP_SAVE_SYN`: порядок
  TCP-опций без учёта NOP, окно, wscale) и шаблону FakeTLS ClientHello:
  шаблон Safari — `Apple` (iOS и macOS неотличимы, неофициальные клиенты на
  коде Telegram-iOS тоже); шаблон Chrome плюс стек Windows
  (`mss,ws,sok[,ts]`) — `Windows`; плюс стек Linux (`mss,sok[,ts],ws`) —
  `Android` (окно 65535 или wscale ≥ 8) или `Linux` (wscale ≤ 7); плюс стек
  Apple — `Apple` (Telegram Desktop на macOS); остальное — `Undefined`. TTL
  не учитывается: его часто переписывают (64 или 128), чтобы оператор не
  видел раздачу интернета. VPN, который сам держит TCP (прокси-типа),
  подменяет SYN: тогда платформа будет ОС самого VPN.
- **ME-маршрут, направление вниз.** Соединение с Middle-End общее для многих
  клиентов, его нельзя притормозить ради одного. Перерасход ведра
  приостанавливает чтение запросов этого клиента, поэтому замедляются загрузки,
  вызванные запросами; один большой ответ может кратко превысить лимит. На
  прямом маршруте лимит точный.
- Соединение, которое прокси держит на паузе по лимиту скорости, не
  закрывается по `idle_timeout`: тишина — не простой клиента.

Политика хранится в `users.json`. Файл пишется в версии `2`, только если хотя
бы у одного пользователя задана политика; иначе остаётся версия `1`, и старые
сборки mtdd продолжают его читать. Израсходованная квота хранится отдельно, в
`usage_state_path` (установщик задаёт `/var/lib/mtdd/usage.json`), чтобы трафик
не переписывал `users.json` и не двигал ревизию:

- файл пишется атомарно с правами `0600` раз в 60 секунд, если есть изменения,
  и при штатной остановке; при аварийном падении теряется не больше минуты
  учёта (и сброс квоты, сделанный в эту минуту);
- чужой владелец, доступ группе или остальным, симлинк или повреждённый файл
  останавливают запуск: молча обнулить квоты всем хуже, чем не стартовать;
- без `usage_state_path` расход живёт только в памяти и обнуляется при
  перезапуске.

## Подмена рекламного тега

`POST /v1/ad-tag` с телом `{"ad_tag":"<32 hex, не все нули>"}` меняет тег без
перезапуска: реакторы подхватывают его на ближайшем такте обслуживания (около
секунды), открытые соединения с Middle-End передают новый тег в следующем
`RPC_PROXY_REQ`, клиенты не переподключаются. `DELETE /v1/ad-tag` возвращает тег
из `ad_tag` конфигурации. Подмена не записывается в файл: после перезапуска
действует тег из конфигурации. `GET /v1/ad-tag` показывает
`{"override": true|false, "ad_tag": "<hex>"|null}`. Каждая подмена и возврат
попадают в журнал событий (`ad_tag.override`, `ad_tag.reset`).

## Шейпинг медиа

Правила шейпинга медиа из конфигурации (`shaping`, см.
[CONFIG.md](CONFIG.md#шейпинг-медиа)) можно временно подменить без
перезапуска. Подмена не записывается в файл: после перезапуска действуют
правила из конфигурации.

`GET /v1/shaping` (read) показывает действующие правила, их источник и живые
счётчики:

```json
{"ok": true, "request_id": 2, "data": {
  "source": "config",
  "effective":  {"media_download": {"user_kbps": 8000, "total_kbps": 0, "burst_kib": 4096, "dcs": []},
                 "media_upload":   {"user_kbps": 0, "total_kbps": 0, "burst_kib": 0, "dcs": []}},
  "configured": {"media_download": {"user_kbps": 8000, "total_kbps": 0, "burst_kib": 4096, "dcs": []},
                 "media_upload":   {"user_kbps": 0, "total_kbps": 0, "burst_kib": 0, "dcs": []}},
  "state": {"media_download": {"active_users": 0, "heavy_users": 0, "light_bytes_per_sec": 0},
            "media_upload":   {"active_users": 0, "heavy_users": 0, "light_bytes_per_sec": 0}}}}
```

| Поле | Значение |
| --- | --- |
| `source` | `config` — правила из файла, `api` — действует подмена |
| `effective` | Правила, которые применяются сейчас |
| `configured` | Правила из файла (после последнего `systemctl reload mtdd`) |
| `state.*.active_users` | Пользователи с активным медиа-соединением правила |
| `state.*.heavy_users` | Пользователи, чьё соединение упиралось в свою долю за последнюю секунду |
| `state.*.light_bytes_per_sec` | Сколько за последнюю секунду передали соединения ниже своей доли |

`PATCH /v1/shaping` (admin) принимает объект в формате ключа `shaping`
конфигурации и **накладывает его на действующие правила**: отсутствующие
правила и поля не меняются, заданный `dcs` заменяет список целиком. Ответ —
то же, что у `GET`, с `source: "api"`. Новые скорости и запас действуют на
открытые соединения, новый `dcs` — на новые соединения.

```bash
curl -s -X PATCH -H "Authorization: Bearer $MTDD_API_TOKEN" \
  -d '{"media_download":{"user_kbps":4000,"burst_kib":2048}}' \
  http://127.0.0.1:9090/v1/shaping
```

`DELETE /v1/shaping` (admin) снимает подмену и возвращает правила из
`configured`.

| Ситуация | Ответ |
| --- | --- |
| Пустой объект `{}` | `400 invalid_field` |
| Неизвестное правило или поле, значение вне диапазона | `400 invalid_field` с ключом в сообщении, например `shaping.media_upload.burst_kib must be 0 or at least 16` |
| `PATCH` или `DELETE` read-токеном | `403 forbidden_scope` |
| Другой метод | `405` |

`systemctl reload mtdd` при активной подмене обновляет только
`configured`: подмена остаётся в силе до `DELETE`, а в журнал пишется строка
`shaping override from the API stays in effect`. Успешные изменения попадают
в журнал событий как `shaping.override` (с именами изменённых полей, без
значений) и `shaping.reset`. Из лаунчера то же самое делают
`install.sh shaping`, `install.sh shaping set` и `install.sh shaping reset`.

## Статистика

Уникальные IP считаются двумя счётчиками:

- **seen** — адреса, прошедшие рукопожатие с секретом пользователя;
- **active** — адреса, у которых хотя бы одно соединение передало не меньше
  `unique_ip_min_bytes` байт полезной нагрузки (по умолчанию 1 MiB).

Порог считается **на соединение**, а не на сумму по адресу: десяток коротких
проверок связи не делает адрес активным. IPv6 сворачивается до `/64`, поэтому
смена адреса внутри одной сети провайдера не плодит «новых» клиентов.

Окна: `online` (точный подсчёт по текущим соединениям), `hour`, `day`, `week`
(HyperLogLog, ≈1% погрешности). Метрика `mtdd_unique_ips_active` теперь
означает «прошедшие порог трафика»; прежнее значение — `mtdd_unique_ips_seen`.

## Журнал событий

Кольцевой буфер последних 256 успешных изменений в памяти процесса:

```json
{"id": 12, "at": "2026-10-30T09:15:02Z", "action": "user.update", "user": "alice",
 "source": "127.0.0.1", "revision": 31, "request_id": 118, "applied": true,
 "fields": ["enabled", "note"]}
```

`action`: `user.create`, `user.update`, `user.delete`, `user.rotate_secret`,
`user.enable`, `user.disable`, `user.reset_quota`. В событии только имена
изменённых полей — значения, секреты и токены туда не попадают. Неудачные
запросы не записываются. Журнал сбрасывается при перезапуске; для длительного
хранения забирайте его через `after=next_after`.

## Метрики

`/metrics` — текстовый формат Prometheus, все имена с префиксом `mtdd_`.
Рекомендуемая схема — отдельный порт и metrics-токен:

```yaml
scrape_configs:
  - job_name: mtdd
    authorization:
      credentials_file: /etc/prometheus/mtdd-metrics.token
    static_configs:
      - targets: ["127.0.0.1:9091"]
```

Метрики шейпинга (`mtdd_shaping_*`, `mtdd_media_*throttled_total`,
`mtdd_user_rate_*`) описаны в [CONFIG.md](CONFIG.md#метрики-шейпинга).

## Отличия от telemt

Набор возможностей взят у telemt (политики пользователей, статистика,
системная информация), но его слабые места закрыты:

| В telemt | Почему плохо | В mtdd |
| --- | --- | --- |
| `listen = 0.0.0.0:9091`, пустой `auth_header` по умолчанию | API без авторизации, защищён только whitelist | Петлевой адрес, токен обязателен |
| Один `auth_header`, `read_only` — глобальный флаг | Мониторингу нельзя выдать доступ «только смотреть» | Три токена: admin, read, metrics |
| `GET /v1/users` отдаёт ссылки с секретами | Обычный список сливает все секреты | Секрет только при создании, ротации и в `/links` |
| Сырые IP клиентов в ответах | Приватность | Только числа; адреса не хранятся |
| Дубли маршрутов (`me_pool_state` и `me-pool-state`), алиасы | Двусмысленность, расползание | Один стиль, без алиасов |
| Около 50 маршрутов, многие — внутренности | Трудно поддерживать и понять | Около 20 маршрутов |
| Конфликт `If-Match` — `409` | Не по RFC 9110 | `412` |
| Нет пагинации и фильтров | Тысячи пользователей — огромный ответ | `limit`, `offset`, `sort`, `enabled` |
| `PATCH /v1/config` правит почти весь конфиг | Большая поверхность атаки | Конфиг только на чтение и без секретов; на лету меняются только рекламный тег и правила шейпинга, без записи в файл |
| Нет журнала действий администратора | Не понять, кто отключил пользователя | `GET /v1/events` |
