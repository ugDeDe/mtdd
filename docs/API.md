## Подключение и токены

```
              control_host:control_port (127.0.0.1:9090)
 admin ─────►  /v1/*  (все маршруты)
 read  ─────►  /v1/*  (только GET, без ссылок и /metrics)

              metrics_host:metrics_port (127.0.0.1:9091)
 metrics ───►  /metrics  (только он; /v1/* здесь — 404)
```

| Токен | Переменная окружения (имя задаёт конфиг) | Что разрешено |
| --- | --- | --- |
| admin | `api_token_env` | Всё на API-порту, включая изменения и `/metrics` (устарело, см. ниже) |
| read | `api_read_token_env` | Только `GET`; запрещены `/v1/users/{name}/links` (в ссылке секрет) и `/metrics` |
| metrics | `metrics_token_env` | Только `GET /metrics` на порту метрик |

Токены передаются заголовком `Authorization: Bearer TOKEN` и сравниваются за
постоянное время. Неверный токен — `401` с `WWW-Authenticate`, недостаточная
область — `403 forbidden_scope`.

- `control_allow` / `metrics_allow` — списки сетей (`10.0.0.0/8`, `::1`);
  пустой список пускает всех, иначе чужой адрес получает `403`.
- `metrics_port: 0` выключает отдельный слушатель. Непетлевой `metrics_host`
  без токена и без явного `metrics_allow` — ошибка конфигурации.
- `/metrics` на API-порту оставлен для совместимости, отвечает с
  `Deprecation: true` и принимает только admin-токен.
- Частота запросов ограничена на источник и глобально; превышение — `429` с
  `Retry-After: 1`.

Не публикуйте API в недоверенную сеть: это обычный HTTP без TLS.

## Формат ответа

Каждый JSON-ответ — объект с конвертом:

```json
{"ok": true, "request_id": 41, "data": { ... }}
{"ok": false, "request_id": 42, "error": {"type": "not_found", "message": "user not found"}}
```

- `request_id` растёт монотонно в пределах процесса и дублируется в заголовке
  `X-Request-Id`; он же записывается в [журнал событий](#журнал-событий).
- Все ответы — `Cache-Control: no-store`.
- Ответы о пользователе несут `ETag: "REVISION"`. Изменения принимают
  `If-Match: "REVISION"`; устаревшая ревизия — `412 revision_conflict`.
- `202` означает, что изменение записано, но рантайм ещё не подтвердил
  применение.
- Время — RFC 3339 в UTC (`2030-01-01T00:00:00Z`). На вход принимается `Z` или
  смещение `±HH:MM`; дробные секунды отбрасываются.

## Ошибки

| HTTP | `error.type` | Когда |
| --- | --- | --- |
| 400 | `invalid_json`, `invalid_request`, `invalid_field`, `unknown_field`, `invalid_name`, `invalid_query` | Неверное тело, поле или строка запроса |
| 401 | `unauthorized` | Нет или неверный токен |
| 403 | `forbidden`, `forbidden_scope` | Адрес вне allowlist или недостаточная область токена |
| 404 | `not_found` | Нет маршрута или пользователя |
| 405 | `method_not_allowed` | Метод не поддерживается маршрутом |
| 409 | `duplicate_name`, `duplicate_secret` | Конфликт при создании |
| 412 | `revision_conflict` | `If-Match` не совпал |
| 413 | `body_too_large` | Тело больше лимита |
| 429 | `rate_limited` | Превышена частота запросов |
| 500 | `io_error` | Ошибка записи состояния |
| 503 | `overloaded` и др. | Перегрузка; для `/links` — не задан `public_host` |

Неизвестные параметры строки запроса, их повторы и значения вне диапазона —
всегда `400 invalid_query`: опечатка не должна молча менять выборку.

## Маршруты

| Метод и путь | Область | Назначение |
| --- | --- | --- |
| `GET /v1/health` | read | Процесс API жив |
| `GET /v1/ready` | read | Есть включённый пользователь и готов ME |
| `GET /v1/status` | read | Сводные счётчики и пулы ME |
| `GET /v1/system/info` | read | Версия, uptime, `started_at`, pid, потоки, ревизия, профиль безопасности |
| `GET /v1/config` | read | Действующая конфигурация без секретов |
| `GET /v1/stats/summary` | read | Пользователи, соединения, трафик, уникальные IP |
| `GET /v1/stats/me` | read | Пулы Middle-End по DC |
| `GET /v1/stats/users` | read | Пользователи, отсортированные по нагрузке |
| `GET /v1/events` | read | Журнал изменений |
| `GET /v1/users` | read | Список пользователей |
| `POST /v1/users` | admin | Создать пользователя |
| `GET /v1/users/{name}` | read | Пользователь со статистикой |
| `PATCH /v1/users/{name}` | admin | Изменить поля |
| `DELETE /v1/users/{name}` | admin | Удалить и отозвать сессии |
| `GET /v1/users/{name}/links` | admin | Ссылки `https://t.me/proxy` и `tg://` |
| `POST /v1/users/{name}/rotate-secret` | admin | Новый секрет, старые сессии отзываются |
| `POST /v1/users/{name}/enable` | admin | Включить |
| `POST /v1/users/{name}/disable` | admin | Выключить и отозвать сессии |
| `POST /v1/users/{name}/reset-quota` | admin | Обнулить счётчик квоты трафика |
| `GET /metrics` | metrics | Prometheus (порт метрик) |

`enable`, `disable` и `reset-quota` принимают пустое тело (или `{}`) и
`If-Match`. Повторное действие без изменений не двигает ревизию. Расход квоты
хранится вне `users.json`, поэтому `reset-quota` ревизию не меняет никогда;
`If-Match` сверяется с текущей ревизией.

`/v1/config` и `/v1/system/info` не содержат токенов, секретов и `ad_tag`
(вместо него — `ad_tag_set`). `security` в `/v1/system/info` показывает, на
петлевом ли адресе API и метрики, заданы ли read- и metrics-токены, размер
allowlist, включены ли маскировка и FakeTLS, глобальные лимиты.

### Параметры списков

| Маршрут | Параметры |
| --- | --- |
| `GET /v1/users` | `limit` 1..10000 (по умолчанию все), `offset`, `enabled=true\|false`. Ответ: `users`, `total`, `offset`, `limit` (`null`, если не задан) |
| `GET /v1/stats/users` | `sort=traffic\|connections\|unique_ips\|name` (по умолчанию `traffic`; `unique_ips` — по seen), `limit` 1..1000 (50), `offset`. Ответ: `users` (с `quota_used_bytes` и `data_quota_bytes`), `total` |
| `GET /v1/events` | `after=ID`, `limit` 1..256 (50). Ответ: `events`, `next_after`, `oldest_id`, `capacity` |

## Пользователи и политика

```json
POST /v1/users
{
  "name": "alice",
  "max_connections": 8,
  "expires_at": "2030-01-01T00:00:00Z",
  "data_quota_bytes": 10737418240,
  "max_unique_ips": 3,
  "rate_limit_up_bytes_per_sec": 1048576,
  "rate_limit_down_bytes_per_sec": 4194304,
  "note": "семья · ноутбук"
}
```

| Поле | Тип | Ограничения | Действие при нарушении |
| --- | --- | --- | --- |
| `expires_at` | RFC 3339 \| null | ≥ 1970 | Новые подключения — `user_expired`, активные закрываются |
| `data_quota_bytes` | целое \| null | ≥ 1 | После исчерпания: новые подключения — `user_quota_exceeded`, активные закрываются |
| `max_unique_ips` | целое \| null | 1..2³²−1 | Подключение с нового IP сверх лимита — `user_ip_limit`; уже известный IP пускается всегда |
| `rate_limit_up_bytes_per_sec` | целое \| null | ≥ 1024 | Чтение от клиента приостанавливается, пока ведро не наполнится |
| `rate_limit_down_bytes_per_sec` | целое \| null | ≥ 1024 | То же для ответа Telegram (на ME-маршруте — приближённо, см. ниже) |

`max_connections` сверх лимита теперь отклоняется с причиной
`user_connection_limit` (раньше — общий `overload`). Причины видны в
`mtdd_connections_rejected_total{reason=...}`.
| `note` | строка | ≤ 256 байт UTF-8, без управляющих символов | — |

В `PATCH` поле со значением `null` снимает ограничение, `note: ""` очищает
заметку; отсутствующее поле не меняется. Пустой `PATCH` — `400`.

### Как применяются ограничения

- **Срок и квота** проверяются при рукопожатии и раз в секунду для активных
  сессий. Сессия может превысить квоту на объём трафика за эту секунду.
- **Квота** считает полезную нагрузку в обе стороны (`stats.quota_used_bytes`);
  `stats.quota_reset_at` — время последнего сброса или `null`.
- **Скорость** — GCRA-ведро на пользователя и направление, общее для всех
  потоков; запас (burst) — `max(лимит, 64 KiB)`. Данные не отбрасываются и не
  буферизуются сверх обычного: у источника снимается `EPOLLIN`. `PATCH` лимита
  действует на уже открытые сессии.
- **ME-маршрут, направление вниз.** Соединение с Middle-End общее для многих
  клиентов, его нельзя притормозить ради одного. Перерасход ведра
  приостанавливает чтение запросов этого клиента, поэтому замедляются загрузки,
  вызванные запросами; один большой ответ может кратко превысить лимит. На
  прямом маршруте лимит точный.
- Долгая пауза по лимиту скорости может упереться в `idle_timeout`.

Политика хранится в `users.json`. Файл пишется в версии `2`, только если хотя
бы у одного пользователя задана политика; иначе остаётся версия `1`, и старые
сборки mtdd продолжают его читать. Израсходованная квота хранится отдельно, в
`usage_state_path` (установщик задаёт `/var/lib/mtdd/usage.json`), чтобы трафик
не переписывал `users.json` и не двигал ревизию:

- файл пишется атомарно с правами `0600` раз в 60 секунд, если есть изменения,
  и при штатной остановке; при аварийном падении теряется не больше минуты
  учёта (и сброс квоты, сделанный в эту минуту);
- чужой владелец, доступ группе или остальным, симлинк или повреждённый файл
  останавливают запуск: молча обнулить квоты всем хуже, чем не стартовать;
- без `usage_state_path` расход живёт только в памяти и обнуляется при
  перезапуске.

## Статистика

Уникальные IP считаются двумя счётчиками:

- **seen** — адреса, прошедшие рукопожатие с секретом пользователя;
- **active** — адреса, у которых хотя бы одно соединение передало не меньше
  `unique_ip_min_bytes` байт полезной нагрузки (по умолчанию 1 MiB).

Порог считается **на соединение**, а не на сумму по адресу: десяток коротких
проверок связи не делает адрес активным. IPv6 сворачивается до `/64`, поэтому
смена адреса внутри одной сети провайдера не плодит «новых» клиентов.

Окна: `online` (точный подсчёт по текущим соединениям), `hour`, `day`, `week`
(HyperLogLog, ≈1% погрешности). Метрика `mtdd_unique_ips_active` теперь
означает «прошедшие порог трафика»; прежнее значение — `mtdd_unique_ips_seen`.

## Журнал событий

Кольцевой буфер последних 256 успешных изменений в памяти процесса:

```json
{"id": 12, "at": "2026-10-30T09:15:02Z", "action": "user.update", "user": "alice",
 "source": "127.0.0.1", "revision": 31, "request_id": 118, "applied": true,
 "fields": ["enabled", "note"]}
```

`action`: `user.create`, `user.update`, `user.delete`, `user.rotate_secret`,
`user.enable`, `user.disable`, `user.reset_quota`. В событии только имена
изменённых полей — значения, секреты и токены туда не попадают. Неудачные
запросы не записываются. Журнал сбрасывается при перезапуске; для длительного
хранения забирайте его через `after=next_after`.

## Метрики

`/metrics` — текстовый формат Prometheus, все имена с префиксом `mtdd_`.
Рекомендуемая схема — отдельный порт и metrics-токен:

```yaml
scrape_configs:
  - job_name: mtdd
    authorization:
      credentials_file: /etc/prometheus/mtdd-metrics.token
    static_configs:
      - targets: ["127.0.0.1:9091"]
```

## Отличия от telemt

Набор возможностей взят у telemt (политики пользователей, статистика,
системная информация), но его слабые места закрыты:

| В telemt | Почему плохо | В mtdd |
| --- | --- | --- |
| `listen = 0.0.0.0:9091`, пустой `auth_header` по умолчанию | API без авторизации, защищён только whitelist | Петлевой адрес, токен обязателен |
| Один `auth_header`, `read_only` — глобальный флаг | Мониторингу нельзя выдать доступ «только смотреть» | Три токена: admin, read, metrics |
| `GET /v1/users` отдаёт ссылки с секретами | Обычный список сливает все секреты | Секрет только при создании, ротации и в `/links` |
| Сырые IP клиентов в ответах | Приватность | Только числа; адреса не хранятся |
| Дубли маршрутов (`me_pool_state` и `me-pool-state`), алиасы | Двусмысленность, расползание | Один стиль, без алиасов |
| Около 50 маршрутов, многие — внутренности | Трудно поддерживать и понять | Около 20 маршрутов |
| Конфликт `If-Match` — `409` | Не по RFC 9110 | `412` |
| Нет пагинации и фильтров | Тысячи пользователей — огромный ответ | `limit`, `offset`, `sort`, `enabled` |
| `PATCH /v1/config` правит почти весь конфиг | Большая поверхность атаки | Конфиг только на чтение и без секретов |
| Нет журнала действий администратора | Не понять, кто отключил пользователя | `GET /v1/events` |
