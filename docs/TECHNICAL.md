## Обзор

mtdd — MTProto-прокси для Telegram на C++20 для Linux x86-64. Один
статически слинкованный бинарник обслуживает несколько пользователей с
персональными секретами, терминирует FakeTLS на клиентской стороне и
мультиплексирует логические клиентские соединения через общий пул соединений
с Middle-End (ME) Telegram, выбираемый по точному signed DC. «Статический»
здесь означает отсутствие `DT_NEEDED` у исполняемого файла, а не отсутствие
любых файлов в системе: для HTTPS-загрузки метаданных нужен системный CA
bundle (см. раздел [Преимущества и компромиссы](#преимущества-и-компромиссы)).

Ключевые инженерные решения:

| Решение | Следствие |
| --- | --- |
| epoll-реакторы, по одному на worker | Нет блокировок на горячем пути пересылки |
| Пул ME-writers с масштабированием | Мало соединений к Telegram при любом числе клиентов |
| Явный бюджет буферов (`global_buffer_bytes`) | Буферы пересылки ограничены конфигурацией, а не трафиком |
| API управления + Prometheus-метрики | Эксплуатация без доступа к файлам и логам |
| Офлайн-набор GoogleTest и прогоны ASan/UBSan | Регрессии ловятся без живого Telegram |

> Интерфейсы компонентов разделены по CMake-целям (`mtdd_protocol`, `mtdd_io`,
> `mtdd_control`, `mtdd_runtime`), а зависимости между ними объявлены явно:
> `mtdd_runtime` линкует protocol, control и io; `mtdd_control` использует
> OpenSSL и libevent; `mtdd_protocol` — OpenSSL. Изоляция здесь означает явные
> границы интерфейсов, а не отсутствие зависимостей между слоями.

## Архитектура

```text
Клиент Telegram          mtdd (процесс)                     Telegram
┌──────────────┐  FakeTLS   ┌──────────────────────────┐       ┌──────────┐
│ персональный ├───────────►│ reactor (epoll)          │       │ Middle-  │
│ секрет,      │ TLS + AES- │  ├─ терминация FakeTLS   ├──────►│ End (ME) │
│ ссылка t.me  │ CTR        │  ├─ проверка секрета     │ пул   │ CBC+CRC  │
└──────────────┘            │  ├─ кадры MTProto        │ writers└──────────┘
                            │  └─ привязка к ME-writer │
      Администратор         ├──────────────────────────┤
┌──────────────┐  Bearer    │ control: HTTP API +     │
│ curl / mtdd- ├───────────►│ /metrics (libevent,      │
│ ctl, SSH     │  localhost │  отдельный тред)         │
└──────────────┘            └──────────────────────────┘
```

Компоненты:

- **`protocol/`** — обфускация MTProto (AES-256-CTR), FakeTLS (TLS 1.3-подобное
  рукопожатие; тела ApplicationData шифруются AES-256-CTR), ME-транспорт
  (AES-256-CBC + согласованный CRC-32/CRC-32C), криптопримитивы OpenSSL,
  адреса endpoint'ов ME.
- **`runtime/`** — epoll-реакторы: клиентские сессии, ретрансляция, пулы ME,
  Direct fallback, дренаж и завершение.
- **`control/`** — HTTP API (libevent), хранилище пользователей с ревизиями,
  лимиты допуска, статистика, история IP.
- **`io/`** — сокеты, уникальные дескрипторы, очереди байтов.
- **`src/main.cpp`** — разбор аргументов, блокировка сигналов, сборка
  компонентов и запуск.

## Модель потоков и событийный цикл

- `workers = N > 1` создаёт N слушателей с `SO_REUSEPORT`; ядро распределяет
  TCP-соединения по реакторам. `workers = 0` выбирает число автоматически с
  учётом бюджета памяти. Реактор 0 живёт в вызывающем треде, остальные —
  N−1 воркеров.
- Каждый реактор владеет своими клиентами, своим пулом ME и своими буферами.
  **На горячем пути пересылки пакета нет общих структур и блокировок.**
  Единственное общее межпоточное состояние, не привязанное к реактору, — учёт
  допуска (глобальные лимиты соединений и рукопожатий, replay-кэш, множества
  уникальных IP), готовность и координация остановки; оно не затрагивается на
  каждый пересланный пакет.
- Остановка: `request_stop()` из любого треда пишет в `eventfd`; процесс
  блокирует `SIGINT`/`SIGTERM` до создания тредов, поэтому реактор 0
  устанавливает `signalfd` и инициирует плавное завершение всех реакторов.
- Таймеры (тайм-ауты рукопожатий, простоя, keepalive ME) — в общей куче на
  реактор; за один проход обрабатывается не более 256 сработавших таймеров
  (предел справедливости, чтобы поток active-соединений не голодал цикл).
- Готовые к отправке клиенты из ME обрабатываются батчами по 64
  (`kMeReadyBatch`), запись пакетами до 64 КиБ.

## Работа с Middle-End (ME)

ME — серверная прослойка Telegram, к которой подключаются MTProto-прокси.
Соединение с ME несёт **обязательный рекламный тег** (`ad_tag`); прокси
удерживает несколько долгоживущих TCP-соединений («writers») с ME и
мультиплексирует по ним клиентский трафик.

### Метаданные DC

- Адреса и ключи DC приходят в метаданных: по умолчанию загрузка по HTTPS
  с проверкой сертификата; опционально — локальные файлы `me_config_path` и
  `me_secret_path`.
- Метаданные обновляются раз в `metadata_refresh_seconds` (по умолчанию час).
- Смена метаданных координируется барьером ревизий (`RevisionBarrier`):
  новое поколение соединений подключается «successor-first» — реактор
  считается готовым, только когда все реакторы видят одну ревизию.

### Пул писателей и масштабирование

На каждый signed DC и каждый реактор — отдельный пул:

- Пул стартует с **одного** writer'а; цель масштабирования хранится в
  `scale_target ∈ [1, me_connections_per_dc]` (диапазон конфига 1–24,
  по умолчанию 12).
- Решения о масштабировании принимаются раз в **10 секунд**. Цель сразу
  поднимается до `ceil(клиенты / me_clients_per_writer)` (не выше
  `me_connections_per_dc`), а недостающие writer'ы добираются по тику
  housekeeping не более чем по **4 одновременных подключения/рукопожатия**
  на пул — так рестарт не ждёт по одному writer'у на решение. Writer
  добавляется также, если два подряд замера показали давление (очередь
  writer'а ≥ ¾ `connection_queue_bytes`) и нет незавершённых подключений.
- Неиспользуемый writer перестаёт принимать новых клиентов и удаляется
  только после завершения его сессий и очередей (state `scale_draining`).
- Пределы: на реактор — **63 writer'а** (64 во время замены метаданных —
  резерв под successor), суммарно слотов на DC — `2 × me_connections_per_dc`
  (рабочее поколение + преемник; до 48 при максимуме 24).
- Новый writer создаётся только при наличии в буферном бюджете свободных
  ≥ 64 КиБ (`budget_allows(65536)`), то есть рост пула не может пробить
  бюджет памяти.
- Слоты writer'ов распределяются по списку адресов DC по кругу — при сбоях
  кандидаты меняются, а не долбят один адрес.

### Liveness и повторные попытки

- Keepalive: ME-ping каждые **25 ± 5 с**; три неотвеченных пинга считают
  соединение мёртвым. Замеры RTT публикуются в метрике
  `mtdd_me_ping_rtt_us` (усреднение по окну).
- Переподключение: экспоненциальная задержка `500 мс × 2^попытка` с потолком
  **30 с** и джиттером ±25 % (минимум 100 мс), чтобы рестарты ME не
  превращались в синхронный шторм.
- Отложенные `RPC_CLOSE_CONN` для уже закрытых логических соединений
  ограничены политикой `RemoteCloseControl`: очередь не растёт бесконечно,
  дубликаты conn-id схлопываются в окне 2 с, на окно действует бюджет
  отправки — обратная связь от ME не может стать усилителем трафика.
- При потере writer'а его клиентские сессии закрываются; клиенты
  переподключаются стандартным образом. Перепривязка живой сессии на другой
  writer не выполняется — состояние MTProto-сессии неразрывно связано с
  соединением ME.

### Замена метаданных и дренаж

Соединение, обслуживаемое по устаревшим метаданным, уходит в дренаж **только
после того, как** преемник того же DC достиг готовности: готовность никогда
не зависит от закрываемого соединения. Дренажное соединение обслуживает лишь
уже привязанных клиентов и снимается при нуле клиентов либо по жёсткому
дедлайну **300 секунд** — что наступит раньше.

### Direct fallback

Опционально (`direct_fallback_enabled` + список `direct_fallback_dcs`)
аутентифицированные клиенты выбранных DC обслуживаются напрямую через
доверенную таблицу официальных адресов DC (транспорт obfuscated2, ответ
пере-упаковывается в клиентский padded intermediate). Прямые маршруты
**не несут рекламный тег ME**. Отдельно существует raw-TLS-fallback для
непрошедших аутентификацию ClientHello (`masking`, по умолчанию включён).
Это байтовый релей, а не TLS/HTTP-реализация. При заданных
`fallback_host`/`fallback_port` проба уходит на фиксированную цель; иначе,
если SNI принадлежит `tls_domain` (сам домен или поддомен), — на настоящий
сервер этого имени на 443, поэтому активная проба получает подлинный
сертификат; при чужом или отсутствующем SNI и для байтов, которые вовсе не
TLS, — на настоящий сервер `tls_domain`:443, который и отвечает пробе.
`masking: false` без фиксированной цели закрывает пробы.
Fallback не связан с Direct, не создаёт пользовательскую сессию и не
применяется к уже аутентифицированным сессиям; он также не доказывает
маскировку Telegram-трафика.

## Протокол клиента: обфускация и FakeTLS

Порядок строго такой: сначала TLS-рукопожатие FakeTLS, затем **внутри его
ApplicationData** — обфускация MTProto (obfuscated2). Обратный порядок
(«сначала obfuscated2, затем TLS») коду не соответствует:
`FakeTlsConnection::State` проходит `ClientHello` → `Obfuscation` → `Ready`
(`include/mtdd/protocol.hpp`, `src/protocol/fake_tls.cpp`).

1. Клиент открывает TCP и отправляет **TLS-запись ClientHello** (`0x16`,
   TLS 1.3-совместимые cipher suites, SNI). В 32-байтовом слоте случайного
   значения ClientHello лежат первые 28 байт HMAC-SHA256; последние 4 байта
   этого слота XOR-ом с последними 4 байтами канонического HMAC кодируют
   метку времени; SNI должен совпадать с `tls_domain` (ASCII без учёта
   регистра).
2. Прокси проверяет ClientHello по каждому включённому секрету
   (`validate_client_hello`): версия и длины записей, наличие TLS 1.3
   cipher, канонический HMAC и окно времени ±120 с. Проверка секрета и
   **replay-кэш** (отказ повторных ClientHello) выполняются до любого ответа.
3. При успехе прокси отвечает ServerHello (`0x16`), ChangeCipherSpec (`0x14`)
   и одной записью ApplicationData (`0x17`) длиной **2878 байт**. Содержимое
   этой записи — синтетический случайный «слепок» зашифрованного полёта
   сервера, а **не настоящий сертификат и не цепочка X.509**. Он нужен,
   чтобы форма рукопожатия была похожа на TLS 1.3; клиент, который проверяет
   сертификат по-настоящему, такую подмену не примет. Аутентификация здесь
   держится на общем секрете, а не на PKI.
4. Следом клиент присылает **64-байтовый obfuscated2-handshake внутри
   TLS ApplicationData**. Ключи — это SHA-256 от 32 байт nonce и
   16-байтового секрета; IV не хешируется, а берётся из тех же nonce-байт:
   для decrypt — `raw[40..56]`, для encrypt — обратный порядок `raw[8..56]`,
   байты 32..48 (`src/protocol/fake_tls.cpp:355-361,389-399`).
   Поддерживается только padded-intermediate (`secure`) тег, точный signed
   DC берётся из байтов 60–61.
5. После перехода в `Ready` тела записей ApplicationData расшифровываются
   **AES-256-CTR** теми же obfuscated2-ключами. Отдельной CBC- или
   HMAC-цепочки на клиентских записях нет: HMAC-SHA256 используется только
   в рукопожатии (канонический digest ClientHello/ServerHello), а
   целостность полезной нагрузки обеспечивает MTProto/ME-слой.
6. Серверный кодировщик добавляет к полезной нагрузке **0–3 случайных байта**
   padding (`encode_transport_message()`). Входящий padded-intermediate
   этим не ограничен: декодер для `secure` не знает фактическое число
   padding-байт и отбрасывает только `len % 4` (`decode_frames()` через
   `payload_keep()`),
   поэтому остальные байты остаются в payload. Утверждать, что входящий поток
   всегда содержит не более 3 padding-байт, нельзя. Direct-маршрут вообще
   передаёт байты без пересборки, чтобы не исказить зашифрованные длины/CRC
   (`Runtime::Impl::feed_client_tls()`). Размер кадра ограничен
   `max_frame_bytes` (по умолчанию 2 МиБ), поэтому клиент не может заставить
   прокси выделить произвольный буфер.
7. Replay-защита: ключ — канонический HMAC ClientHello; повтор отклоняется
   без fallback. Насыщение ограниченного кэша тоже отклоняется как
   перегрузка, без fallback.

Секрет в ссылке `t.me/proxy?...` собирается как `ee` + 32 hex-символа
16-байтового секрета + hex(`tls_domain`); прокси использует те же 16 байт
для проверки ClientHello.

### Fallback неаутентифицированных ClientHello

При включённом `masking` (по умолчанию) `process_client_hello()` уходит в
fallback не только для «невалидного», но и для **неаутентифицированного**
ClientHello: после неудачного `authenticate_hello()` вызывается
`start_fallback()` (`src/runtime/client.cpp`). Fallback — это байтовый релей
на реальный origin:

- при заданных `fallback_host`/`fallback_port` — на фиксированную цель;
- иначе, если SNI принадлежит `tls_domain` (сам домен или поддомен), — на
  реальный сервер этого имени на 443, поэтому активная проба получает
  подлинный сертификат;
- иначе (чужой или отсутствующий SNI, байты не TLS) — на реальный сервер
  `tls_domain`:443. Закрытие вместо ответа (RST из-за непрочитанных байтов)
  выделяло бы прокси среди обычных HTTPS-серверов. Цель фиксирована, адрес
  клиент не выбирает.

Fallback не создаёт пользовательскую сессию и не применяется к уже
аутентифицированным сессиям. Целевой origin — фиксированная цель, имя из
SNI, принадлежащее `tls_domain`, либо сам `tls_domain`; если DNS/connect не
удался либо `masking` выключен без фиксированной цели, соединение
закрывается. Replay- и перегруженные
рукопожатия в fallback не попадают: они завершаются `reject_close` раньше.
Это поведение не следует трактовать как гарантию маскировки: релей лишь
отдаёт пробе настоящий сертификат запрошенного имени.

Криптопараметры соответствуют спецификациям MTProto/FakeTLS; примитивы —
OpenSSL EVP (`aes-256-ctr`, `aes-256-cbc`, `HMAC(EVP_sha256)`, `RAND_bytes`),
на x86 задействованы аппаратные ускорения AES-NI. Сторона ME использует
AES-256-CBC и CRC, согласованный в `RPC_HANDSHAKE` (IEEE CRC-32 либо
CRC-32C); это отдельный от клиентского транспорта слой.

## Модель памяти

mtdd ограничивает **буферы пересылки** конфигурацией, а не реакцией на OOM.
Это не жёсткий лимит RSS: бюджет учитывает ёмкости буферов, которыми владеет
процесс, но не ядро, аллокатор и управляющую плоскость.

### Бюджет буферов пересылки

- `global_buffer_bytes` (по умолчанию 64 МиБ) — общий бюджет буферов
  пересылки, который делится между реакторами
  (`src/runtime/runtime_state.cpp`). Каждый реактор получает
  `global_buffer_bytes / workers` и проверяет остаток через `budget_allows()`
  (`src/runtime/maintenance.cpp`).
- Бюджет — это **учётный конверт**, а не отдельный резерв памяти: в него
  зачисляются фактические ёмкости очередей `ByteQueue`, буферов FakeTLS,
  декодера, scratch-буферов и собираемых кадров (`reaccount()` в
  `src/runtime/maintenance.cpp`). Поэтому бюджет и очереди не складываются
  повторно.
- Минимальное требование на реактор: `2 × max_frame_bytes +
  2 × connection_queue_bytes + 64 КиБ`. Конфигурация, в которой явное число
  `workers` не помещается в бюджет, **отвергается на старте** с понятной
  ошибкой; при `workers = 0` число реакторов уменьшается до помещающегося
  (`src/runtime/runtime_state.cpp`).
- Создание нового ME-writer'а и рост структур также проверяют бюджет
  (порог 64 КиБ свободного остатка, `src/runtime/me.cpp`).

### Пер-соединение и пер-writer

- Каждый клиент и каждый ME-writer имеет очередь исходящих байтов,
  ограниченную `connection_queue_bytes` (256 КиБ по умолчанию); переполнение
  — сигнал давления для масштабирования, а не безлимитный рост. Ёмкость
  очереди учитывается внутри `global_buffer_bytes`, а не сверх него.
- Входной буфер writer'а: `2 × (max_frame_bytes + накладные расходы кадра)
  + 64 КиБ`, с потолком 64 МиБ.
- Предел собираемого кадра `max_frame_bytes` ограничивает и размер
  «сборки» кадра из потока.

### Удержания и возвраты

- Праздные буферы удерживают до 64 КиБ «тёплой» памяти (`kIdleRetainedBytes`,
  `kScratchRetainBytes`); ёмкости больше 64 КиБ возвращаются системе, когда
  освобождаются (`release_if_large`). Это убирает пилообразный RSS при
  лопающих передачах без потери производительности на мелких аллокациях.
- Допуск соединений ограничен сверху независимо от бюджета:
  `max_connections` и `max_handshakes` (по умолчанию не заданы — без лимита;
  положительное значение включает общий глобальный лимит), replay-кэш и
  множества уникальных IP — атомарные структуры, общие для реакторов.

### Оценка потребления

Бюджет — это учётная цель для буферов пересылки, а не математическая гарантия
RSS. Полный RSS процесса оценивается отдельно; память ядра в него не входит:

```text
RSS процесса ≈ буферы пересылки (учётная цель около global_buffer_bytes)
             + управляющая плоскость, хранилище пользователей, метаданные
             + служебные структуры реакторов, стеки потоков, аллокатор, OpenSSL
память ядра  ≈ сокетные буферы, page tables и т. п. (вне RSS процесса)
```

Бюджет ограничивает admission новых буферов, но не каждый уже выделенный байт:
временные превышения возможны из-за роста ёмкостей, округления аллокатора и
уже начатых операций. Значения по умолчанию (64 МиБ бюджет, 2 МиБ кадр,
256 КиБ очередь) на 4 worker'ах дают ~16 МиБ учётного бюджета на реактор.
Это с запасом вмещает обязательный минимум `2×2 МиБ + 2×256 КиБ + 64 КиБ`;
сами очереди клиентов и ME уже входят в эти 16 МиБ, поэтому прибавлять их к
бюджету повторно нельзя. Фактический RSS может быть выше бюджета и должен
измеряться на целевой нагрузке.

## Процессор и производительность

- **Без пользовательского мьютекса на установившемся релее.** Горячий путь
  (приём → дешифрование → пересылка) целиком внутри одного реактора, и
  клиентские/ME-соединения не требуют общей блокировки. Это не означает
  отсутствия атомиков на пакет: счётчики ME-запросов и ответов пишутся в
  слот своего реактора (`me_request`/`me_answer` в
  `src/control/statistics.cpp`) и агрегируются при чтении снимка по
  монотонной верхней границе (high-water) затронутых/адресуемых слотов
  (`shard_high_water`); слоты выше этой границы не читаются, а накопленная
  история переживает уменьшение числа worker'ов. Часть общих счётчиков
  (`me_reconnect`, `direct_budget_pause`, ping-счётчики) по-прежнему пишет
  слот 0, а per-worker gauges используют `% worker_count`. Допуск и gauges
  также используют атомарные операции. Relaxed-атомики не устраняют
  межъядерную конкуренцию за кэш-линии.
- **Криптография.** На клиентской стороне тела ApplicationData и
  obfuscated2-транспорт используют AES-256-CTR; на стороне ME —
  AES-256-CBC и согласованный CRC-32/CRC-32C. HMAC-SHA256 встречается только
  в рукопожатии FakeTLS, а не в цепочке записей. OpenSSL EVP на x86
  задействует AES-NI; CRC32C реализован в mtdd (`src/protocol/crypto.cpp`)
  с runtime-диспетчеризацией на SSE4.2 и portable fallback
  (`crypto.cpp:161-242`), а не берётся из OpenSSL. Конкретные цифры зависят
  от платформы и снимаются бенчмарками, а не задаются документацией.
- **Батчинг.** Запись — пакетами до 64 КиБ (`kWriteBatch`), слитая отправка
  нескольких соединений сокращает число системных вызовов (см.
  `tools/bench_fused_send.cpp`); готовые клиенты ME обрабатываются пачками
  по 64; таймеры — до 256 за проход цикла.
- **Масштабирование по worker'ам, а не линейно по ядрам.** `workers = N`
  создаёт N реакторов с `SO_REUSEPORT`; ядро распределяет входящие
  соединения. Выигрыш от роста N зависит от числа ядер, равномерности
  распределения, общего admission-состояния, памяти на реактор и характера
  нагрузки, поэтому линейного масштабирования никто не гарантирует.
  Значение `0` выбирает число по `hardware_concurrency()` и уменьшает его,
  если бюджет памяти не вмещает минимум на реактор. Конкретную ёмкость
  следует измерять на целевой конфигурации.
- **Число writers ME** не измерено как «почти не влияющее» на CPU: writer'ы
  долгоживущие, но каждый добавляет соединение, keepalive и обработку
  событий. Влияние зависит от нагрузки и проверяется замерами, а не
  предполагается.
- **Бенчмарки в репозитории**: `tools/bench_crypto.cpp`,
  `tools/bench_fake_tls.cpp`, `bench_fused_send.cpp`, `bench_me.cpp` и
  генератор нагрузки `tools/loadgen` с мониторингом `tools/monitor_load.py` —
  используются для регрессионных замеров при изменениях горячего пути.

## Надёжность и жизненный цикл

| Механизм | Поведение |
| --- | --- |
| Тайм-аут рукопожатия | `handshake_timeout_seconds` (15 с): медленный/зависший ClientHello закрывается |
| Тайм-аут простоя | `idle_timeout_seconds` (1800 с): молчащие сессии закрываются |
| Полузакрытие и дренаж | EOF со стороны клиента/ME дренажируется с телеметрией; отложенные закрытия применяются батчем (`defer_close`) |
| Плавное завершение | `shutdown_timeout_seconds` (10 с) на реактор; деструктор `Runtime` не оставляет разрушенных состояний |
| Ошибки writer'а | Экспоненциальный retry с джиттером; пул не collapses: сбой одного DC не затрагивает другие |
| Перезапуск службы | `Restart=on-failure`, `RestartSec=3`; готовность проверяйте `/v1/ready` и живым клиентом |

Ответ `202` от мутаций API означает, что изменение ещё применяется
(барьер ревизий между API и реакторами) — идемпотентные повторы безопасны.

## Плоскость управления (API)

- HTTP-сервер на libevent в отдельном треде; маршруты `/v1/*` и `/metrics`
  требуют `Authorization: Bearer`; токен никогда не пишется в JSON и берётся
  из переменной среды (`api_token_env`).
- Допуск запросов ограничен гейтом (`connection_gate`) — rate limit и
  одновременные соединения, чтобы API оставался отзывчивым при деградации.
- Мутации пользователей проходят через хранилище с ревизиями
  (`revision`), атомарную запись файла и проверку владения файлом;
  конкурентные изменения разрешаются через `ETag`/`If-Match`.
- Ответы API помечены `Cache-Control: no-store`; секреты возвращаются один
  раз (создание, ротация) или внутри ссылок.
- Три области токенов: admin (всё), read (только `GET`, без ссылок) и
  metrics (только `/metrics` на отдельном слушателе `metrics_host:metrics_port`).
  Каждый ответ несёт `ok` и `request_id` (он же в `X-Request-Id`).
- Журнал изменений — кольцо из 256 событий в памяти треда API; в событии
  только имена полей, без значений и секретов.
- Политика пользователя (срок, квота, лимит IP, скорость) лежит в
  `users.json` (версия 2 только при заданной политике), а расход квоты — в
  отдельном `usage_state_path`: трафик не двигает ревизию хранилища.
- Срок и квота проверяются при рукопожатии и периодическим проходом раз в секунду;
  лимит скорости — lock-free GCRA в `UserMetrics`, общий для всех реакторов:
  при перерасходе у источника снимается `EPOLLIN`, возобновление встроено в
  таймаут `epoll_wait`. Пользователь без лимита платит одной проверкой.

Полный справочник маршрутов — [API.md](API.md).

## Наблюдаемость

`/v1/status` отдаёт сводные счётчики (активные соединения, принятые и
отклонённые подключения, рукопожатия по результатам, аптайм) и срез по DC
(`me_dcs`: соединения, готовые, переподключения). `/metrics` — формат
Prometheus; полезные семейства:

| Метрика | Смысл |
| --- | --- |
| `mtdd_me_pool_connections`, `mtdd_me_pool_ready`, `mtdd_me_pool_target` | Текущий, готовый и целевой размер пула ME по DC |
| `mtdd_me_bound_clients` | Клиенты, привязанные к writer'ам DC |
| `mtdd_me_scale_up_total`, `mtdd_me_scale_down_total` | События расширения и сокращения пула |
| `mtdd_me_creation_failures_total` | Неудачи создания writer'ов (в т.ч. по бюджету) |
| `mtdd_me_ping_rtt_us` | RTT keepalive до ME |
| `mtdd_me_pings_total` | Отправленные keepalive по исходу |

Значения по DC суммируются по реакторам. Для аварийного анализа пишется
телеметрия дренажа и закрытий (счётчики `sweeps`/`closes`/`pumps` и др.),
доступная через статус.

### Дашборд лаунчера и история

`mtdd-ctl metrics` объединяет `/v1/status` и `/metrics` в один экран: пулы и
RTT ME, очереди ready-клиентов, буферы, причины отказов, уникальные IP и
спарклайны динамики. `--watch` перерисовывает дашборд раз в две секунды и
читает клавишу `q` с управляющего терминала.

Снимки для графиков пишутся в `/var/lib/mtdd/metrics-history.tsv` (root,
0600, TSV: время, соединения, уникальные IP, суммарный трафик, средний RTT,
DC в сети, отказы, принятые). Точка добавляется при `status`/`metrics`, но не
чаще раза в 25 секунд; файл ограничен 5000 строками. Дашборд только читает
готовые метрики API и не влияет на прокси; секретов и адресов клиентов в
истории нет.

## Безопасность

- Служба systemd работает от непривилегированного пользователя `mtdd` с
  `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome=true`,
  `PrivateTmp=true`, `ReadWritePaths=/var/lib/mtdd` и единственной
  capability `CAP_NET_BIND_SERVICE`.
- Разграничение файлов: конфигурация `root:mtdd 0640`, токен `root 0600`,
  пользователи `mtdd 0600`. Хранилище пользователей проверяет владельца
  файла и отказывается работать с файлом чужого владельца под root.
- API по умолчанию слушает только loopback; не-loopback требует явного
  `allow_remote_control=true`. Для удалённого администрирования — SSH-туннель.
- Секреты пользователей существуют в трёх местах: хранилище, ответ API при
  создании/ротации, ссылка. Никаких журналов секретов прокси не пишет.

## Преимущества и компромиссы

Преимущества реализации:

1. **Один статически слинкованный бинарник** (`tools/build-static.sh`
   закрепляет версии OpenSSL-совместимой сборки, libcurl, libevent,
   nlohmann/json и проверяет отсутствие `PT_INTERP`/`DT_NEEDED`).
   «Статический» не означает «без данных в системе»: для HTTPS-загрузки
   метаданных нужен системный CA bundle (например,
   `/etc/ssl/certs/ca-certificates.crt`); при использовании локальных
   `me_config_path`/`me_secret_path` он не требуется. Также нужны обычные
   системные DNS-настройки.
2. **Предсказуемые буферы, но не жёсткий RSS-лимит**: бюджет буферов
   проверяется на старте и при росте пулов; соединения ограничены лимитами;
   очередь кадра ограничена конфигом. Управляющая плоскость, аллокатор и
   сокетные буферы ядра в бюджет не входят.
3. **Производительность на worker**: epoll-реакторы без блокировок на
   горячем пути, батчинг записи и слитая отправка, аппаратный AES. Это
   архитектурные свойства, а не обещание конкретного ускорения.
4. **Устойчивость ME**: пул с масштабированием по давлению, successor-first
   замена метаданных, дренаж с дедлайном, retry с джиттером, bounded-политики
   против усилений.
5. **Эксплуатируемость**: лаунчер `mtdd-ctl`, HTTP API с ревизиями и ETag,
   Prometheus-метрики, systemd-харненинг, понятные ошибки конфигурации.
6. **Верифицируемость**: офлайн-набор GoogleTest, отдельные ASan/UBSan-прогоны,
   интеграционные смоуки, установочные тесты в изолированных namespace.

Компромиссы, о которых стоит знать:

- Пул ME **на каждый реактор**: суммарное число соединений к Telegram равно
  `workers × writers`; это плата за отсутствие блокировок.
- При потере writer'а его сессии рвутся (перепривязки нет) — клиенты
  переподключаются сами; это соответствует семантике MTProto-сессий.
- Проект — один прокси для одного сервера, а не панель управления флотом VPS.
- `me_clients_per_writer = 400` — стартовая настройка, а не измеренный
  предел Telegram; под реальную нагрузку значения стоит калибровать метриками.

## Тестирование и верификация

- **Офлайн-набор** (без сети): `ctest --test-dir build --output-on-failure` —
  GoogleTest-набор по протоколу, FakeTLS, рантайму (жизненный цикл, релей,
  direct), control (HTTP, конкурентность, статистика), ME-аудиту, retry и io.
  Точное число тестов зависит от ревизии и конфигурации; актуальный список
  даёт `ctest --test-dir build -N`.
- **Санитайзеры**: сборка `-DMTDD_SANITIZE=ON`, прогон с
  `ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1`.
- **Установщик и лаунчер**: `python3 -m unittest discover -s tests/unit
  -p 'installer_test.py'` — скачивание, контрольные суммы, интерактивный
  ввод, обновление и команды управления в изолированных mount namespace
  (`unshare`), включая тесты против мока API.
- **Интеграционные смоуки** (`tests/integration/`): контрольный API,
  статистика IP, site-proxy, живой ME — требуют отдельного разрешения.
- **Покрытие**: `-DMTDD_COVERAGE=ON` + `python3 tools/coverage_report.py BUILD_DIR`;
  пороговые значения не навязаны. Исторические отчёты предыдущих волн не
  входят в этот репозиторий и не должны использоваться как актуальные
  измерения.
