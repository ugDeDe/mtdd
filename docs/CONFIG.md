## Файл конфигурации

Конфигурация — один JSON-объект. Установщик пишет его в
`/etc/mtdd/config.json`, шаблон для ручного запуска —
[config.example.json](../config.example.json).

- Обязателен только `tls_domain`. Остальные параметры можно не указывать:
  действует значение по умолчанию.
- Неизвестный ключ — ошибка (`unknown configuration option: ...`), а не
  молчаливый пропуск: опечатка не превращается в незаметно выключенную
  настройку.
- Относительные пути считаются от каталога файла конфигурации.
- Размеры — в байтах, если в имени параметра не сказано иное (`_kbps`,
  `_kib`, `_ms`, `_seconds`, `_hours`).
- Токены в файле не хранятся: конфиг содержит только **имена** переменных
  окружения, в которых они лежат (установщик кладёт их в
  `/etc/mtdd/credentials.env`).

Минимальная конфигурация для ручного запуска:

```json
{
  "tls_domain": "example.org",
  "users_path": "runtime/users.json"
}
```

Проверить файл, не запуская прокси:

```bash
./build/mtdd --config config.local.json --check-config
```

Установленный бинарник проверяет конфигурацию командой
`install.sh check-config`. Проверка не обращается к Telegram и не проверяет
пересылку трафика.

## Применение изменений

Без обрыва клиентов, командой `systemctl reload mtdd` (SIGHUP), применяются:

| Параметр | Что происходит |
| --- | --- |
| `me_clients_per_writer`, `me_connections_per_dc`, `me_connections_per_dc_total` | Новые пределы пула ME; живые writers не закрываются |
| `shaping` (и устаревшие `media_user_rate_kbps`, `media_total_rate_kbps`) | Скорости и `burst_kib` — сразу для открытых соединений; изменённый `dcs` — для новых соединений. Если правила подменены через API (`PATCH /v1/shaping`), подмена остаётся в силе до `DELETE /v1/shaping` |

Если перечитанный файл некорректен, прокси пишет в журнал
`reload rejected, keeping current settings` и продолжает работать со старыми
значениями. Остальные параметры применяются только после перезапуска
(`systemctl restart mtdd`).

## Слушатели и доступ к API

| Параметр | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `proxy_host` | строка | `127.0.0.1` | числовой IPv4/IPv6 | Адрес клиентского порта. Установщик ставит `0.0.0.0` |
| `proxy_port` | целое | `14443` | 1..65535 | Клиентский порт |
| `public_host` | строка | пусто | IP или DNS-имя, не `0.0.0.0`/`::` | Адрес в ссылках `t.me/proxy` и `tg://` |
| `public_port` | целое | `proxy_port` | 1..65535 | Порт в ссылках (например, снаружи 443 при локальном 14443 за NAT) |
| `control_host` | строка | `127.0.0.1` | числовой IP | Адрес API управления |
| `control_port` | целое | `9090` | 1..65535, не пересекается с клиентским портом | Порт API |
| `allow_remote_control` | логическое | `false` | | `true` разрешает `control_host` вне loopback. Включайте только в защищённой сети или через туннель: API — HTTP без TLS |
| `api_token_env` | строка | `MTDD_API_TOKEN` | имя переменной `[A-Za-z0-9_]` | Переменная с admin-токеном (32–512 печатных символов без пробелов). Если переменная не задана или пуста, прокси стартует без API; заданное, но некорректное значение останавливает запуск |
| `api_read_token_env` | строка | пусто | имя переменной, отличное от остальных | Переменная с read-токеном: только `GET`, без ссылок с секретами. Пусто — read-токена нет |
| `control_allow` | массив строк | `[]` | до 64 IP или CIDR | Кому разрешено обращаться к API. Пустой список — любому адресу с токеном |
| `metrics_host` | строка | `127.0.0.1` | числовой IP | Адрес отдельного слушателя `/metrics` |
| `metrics_port` | целое | `9091` | 0..65535 | Порт `/metrics`; `0` выключает слушатель |
| `metrics_token_env` | строка | пусто | имя переменной, отличное от остальных | Переменная с токеном для `/metrics` |
| `metrics_allow` | массив строк | `["127.0.0.0/8", "::1"]` | до 64 IP или CIDR | Кому разрешено читать `/metrics` |
| `proxy_protocol` | логическое | `false` | | PROXY protocol v1/v2 (HAProxy) на клиентском порту, для доверенного фронта: SNI-роутера или балансировщика |
| `proxy_protocol_allow` | массив строк | `["127.0.0.0/8", "::1"]` | до 64 IP или CIDR, непустой при `proxy_protocol` | С каких адресов принимается заголовок PROXY |

Ограничения на сочетания:

- Слушатель метрик требует `metrics_token_env` или непустой `metrics_allow`.
  Непетлевой `metrics_host` без токена требует явно заданного
  `metrics_allow`.
- Переменные admin-, read- и metrics-токенов должны различаться, как и сами
  токены.
- Клиентский порт, API, метрики и `fallback_port` не должны пересекаться.

При `proxy_protocol: true` каждое соединение обязано начинаться с заголовка
PROXY и приходить с адреса из `proxy_protocol_allow`, иначе оно закрывается с
причиной `invalid_request`. Адрес из заголовка считается адресом клиента
везде: лимиты IP, статистика, подозрительные адреса, `watch_ips`, адрес для
Telegram. Заголовки `LOCAL`/`UNKNOWN` (проверки здоровья фронта) оставляют
адрес сокета и не попадают в подозрительные. Маскировка получает поток без
заголовка. TCP-отпечаток (`fingerprint`) за фронтом не снимается.

Токены, области доступа и маршруты описаны в
[API.md](API.md#подключение-и-токены).

## FakeTLS и маскировка

| Параметр | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `tls_domain` | строка | — (обязателен) | DNS-имя | Домен FakeTLS: SNI в ссылках и сайт, который видит активная проба |
| `ad_tag` | строка | не задан | 32 hex, не все нули | Рекламный тег Telegram (спонсорский канал). Без него прокси работает без канала |
| `masking` | логическое | `true` | | Релеить неаутентифицированные ClientHello на настоящий сайт |
| `masking_scope` | строка | пусто | 1..32 символа `[A-Za-z0-9_.-]`, такая область должна быть у одного из `upstreams` | Через какие апстримы идёт маскировка (аналог `tls_fetch_scope` у telemt); пусто — общая область |
| `fallback_host` | строка | `127.0.0.1` | IP или DNS-имя, не `0.0.0.0`/`::` | Фиксированная цель маскировки (вместе с `fallback_port`) |
| `fallback_port` | целое | `0` | 0..65535 | Ненулевой порт фиксирует цель маскировки на `fallback_host:fallback_port` вместо SNI |
| `client_clock_skew_seconds` | целое | `120` | 0..86400 | Допустимое расхождение часов клиента по метке времени в ClientHello |
| `server_hello_delay_min_ms`, `server_hello_delay_max_ms` | целое | `0`, `0` | 0..1000, `min` ≤ `max`; `max` по умолчанию равен `min` | Ручная задержка ответа FakeTLS, случайно из `[min, max]` для каждого соединения |
| `server_hello_delay_auto` | логическое | `true` | | Автоматическая задержка по измерению настоящего сервера (если обе ручные границы равны 0) |

**Маскировка.** ClientHello, не прошедший аутентификацию, релеится на реальный
сервер запрошенного SNI, если имя принадлежит `tls_domain` (сам домен или
поддомен): активная проба получает настоящий сертификат. Чужой или
отсутствующий SNI, а также байты, которые вовсе не TLS (HTTP-запрос, текст),
релеятся на сам `tls_domain:443`: пробе отвечает настоящий сайт, а не RST.
Повторный (replay) ClientHello релеится так же. При ошибке DNS или подключения,
а также при `masking: false` соединение закрывается.

Реальный сервер каждого маскируемого домена (`tls_domain` и личные домены
пользователей) периодически опрашивается обычным TLS 1.3-рукопожатием, и ответ
FakeTLS повторяет его: размер зашифрованного первого полёта, шифр, порядок
расширений ServerHello и группу ключа (X25519, если сервер не отвечает
X25519MLKEM768). До первого замера используется прежний ответ.

**Часы клиента.** ClientHello с верным секретом, но вне окна
`client_clock_skew_seconds`, отклоняется как неаутентифицированный и
учитывается в `mtdd_handshake_clock_skew_total`. Кеш повторов хранит
рукопожатия 2 × окно + 30 с. `0` выключает проверку метки времени; тогда
защита от повторов держится только на кеше с хранением 1 ч.

**Задержка ServerHello.** Настоящий сервер отвечает после своего обмена
ключами и подписи. Ручная задержка добавляется к установке **каждого**
Telegram-соединения, поэтому включайте её осознанно. Автоматическая
(`server_hello_delay_auto`) действует, только если обе ручные границы равны 0:
фоновая проба маскировки раз в несколько часов измеряет у каждого
маскируемого домена время от ClientHello до первого байта ServerHello за
вычетом RTT TCP, хранит медиану и разброс p25–p75 по 8 замерам и задерживает
ответ на случайное время из разброса, но не больше 100 мс. Пока домен не
измерен, задержки нет. Пока ответ задержан, данные клиента не читаются.
Меняется только время ответа, не байты рукопожатия. Метрики:
`mtdd_server_hello_auto_delay_total{delay}`,
`mtdd_server_hello_auto_delay_us_total`,
`mtdd_masking_server_processing_us{domain,quantile}`,
`mtdd_masking_server_processing_samples{domain}`.

## Пользователи и файлы состояния

| Параметр | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `users_path` | строка | `users.json` | путь | Хранилище пользователей и их политик. Установщик: `/var/lib/mtdd/users.json` |
| `usage_state_path` | строка | не задан | путь, отдельный файл | Израсходованная квота пользователей. Без него расход живёт в памяти и обнуляется при перезапуске. Установщик: `/var/lib/mtdd/usage.json` |
| `unique_ip_stats_path` | строка | не задан | путь, отдельный файл | Контрольные точки HLL для статистики уникальных IP |
| `unique_ip_min_bytes` | целое | `1048576` | 0..2⁴⁰ | Сколько байт полезной нагрузки должно передать соединение, чтобы его IP считался «активным» уникальным. `0` — активен сразу после рукопожатия |
| `device_window_seconds` | целое | `900` | 60..86400 | Сколько ключ устройства без соединений ещё числится в счётчике устройств (никого не блокирует) |

Файлы состояния должны отличаться друг от друга, от `users_path` и от
локальных файлов метаданных ME. Формат `users.json`, политики пользователей
(срок, квота, лимиты IP, устройств и скорости) и хранение квоты описаны в
[API.md](API.md#пользователи-и-политика).

## Middle-End и Direct

| Параметр | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `me_connections_per_dc` | целое | `16` | 1..24 | Максимум активных ME writers на signed DC **в каждом reactor**. Это потолок, а не число соединений. Перечитывается по SIGHUP |
| `me_connections_per_dc_total` | целое | `0` | 0..1024 | Предел ME writers на signed DC **для всего процесса**; `0` — без общего предела. Перечитывается по SIGHUP |
| `me_clients_per_writer` | целое | `400` | 1..1000000 | Порог клиентов на writer для роста пула (не жёсткий лимит). Перечитывается по SIGHUP |
| `metadata_refresh_seconds` | целое | `3600` | 60..86400 | Интервал обновления метаданных ME |
| `me_config_path`, `me_secret_path` | строка | не заданы | пути, задаются вместе | Локальные метаданные ME вместо загрузки `getProxyConfig` по HTTPS |
| `me_ipv6` | строка | `"auto"` | `"auto"`, `"on"`, `"off"` | Использование IPv6-адресов ME из `getProxyConfigV6` |
| `me_config_v6_path` | строка | не задан | путь; требует `me_ipv6` не `"off"` | Локальный IPv6-список ME вместо загрузки |
| `me_nat_ip` | строка | пусто | конкретный числовой IP | Адрес, с которого Telegram видит соединения к ME, если он не совпадает с адресом сокета (NAT, туннель с фиксированным выходом); аналог `middle_proxy_nat_ip` у telemt |
| `direct_fallback_enabled` | логическое | `false` | | Включает маршрут Direct для DC из `direct_fallback_dcs` |
| `direct_fallback_dcs` | массив целых | `[]` | signed DC ±1..5 без повторов (без 203/CDN) | DC, которые идут напрямую к официальным адресам Telegram. Рекламный тег по этому маршруту не передаётся |

**Пул writers.** Пул начинает с одного writer и растёт при устойчивой
нагрузке. Неиспользуемый writer перестаёт принимать клиентов и удаляется
только после завершения их сессий и очередей. На каждый reactor действует
общий предел 64 writers, включая резерв для замены метаданных. Значение
400 клиентов на writer — начальная настройка, а не измеренный предел
Telegram. Каждый reactor держит свой пул, поэтому при 8 reactors и
`me_connections_per_dc: 24` к одному DC может быть до 8 × 24 writers; общее
число ограничивает `me_connections_per_dc_total`.

**Общий предел writers.** Первый writer каждого reactor для DC пределом не
учитывается, поэтому ни один reactor не остаётся без соединения (при
`workers` больше предела сумма может его превышать). При замене метаданных
новое поколение поднимается «один к одному» вместо старого, даже если предел
исчерпан. Понижение предела не закрывает живые writers, а только запрещает
новые. Метрики: `mtdd_me_writer_slots`, `mtdd_me_writer_cap_refusals_total`.

**Бюджет и keepalive.** Когда бюджет буферов reactor исчерпан, чтение
ME-сокета приостанавливается. Клиенты останавливаются раньше и возобновляются
позже ME, поэтому общий writer всегда возобновляется первым. Пауза по бюджету
не считается отсутствием keepalive. Writer, не отвечающий на PING, заменяется,
только если одновременно PONG просрочен более 3 с и клиентские запросы
остаются без ответа 60 с: часть хостов ME не шлёт PONG, но исправно передаёт
данные. Последний рабочий writer DC не заменяется, и замен не больше одной
на DC за 10 с. Метрики: `mtdd_worker_me_worst_writer_rtt_us`,
`mtdd_worker_me_slow_writers`, `mtdd_worker_me_slow_evictions_total`.

**IPv6.** `"off"` — только IPv4-список. `"auto"` дополнительно загружает
IPv6-список и подключается к DC по IPv6, только если у DC нет IPv4-адреса или
три попытки подряд по IPv4 не удались: тогда новые подключения этого DC идут
по IPv6 5 минут, затем снова пробуется IPv4. `"on"` — наоборот, сначала IPv6.
Ошибка загрузки IPv6-списка не мешает работе по IPv4: остаётся предыдущий
список. Если задан `me_config_path`, а `me_config_v6_path` нет, IPv6-список
не используется. `me_nat_ip` подменяет адрес только своего семейства.
Метрика переключений: `mtdd_me_family_fallbacks_total`.

**NAT и туннели.** ME привязывает ключи к адресу и порту, с которых Telegram
видит соединение. Через SOCKS5 mtdd берёт их из ответа прокси
(BND.ADDR/BND.PORT). Если прокси или туннель стоит за NAT, задайте внешний
адрес в `me_nat_ip`; порт при этом должен сохраняться. Cloudflare WARP меняет
и адрес, и порт, поэтому ME через WARP не работает: для WARP используйте
Direct (`direct_fallback_enabled` и все нужные DC в `direct_fallback_dcs`).

## Апстримы

`upstreams` задаёт, как исходящие соединения покидают сервер: ME, Direct DC,
маскировка и загрузка метаданных. Без `upstreams` всё идёт напрямую. Формат
повторяет `[[upstreams]]` telemt, поэтому менеджеры вроде MTProxyL переносят
настройки один к одному.

| Поле | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `type` | строка | `"direct"` | `"direct"`, `"socks5"` | Напрямую с этого сервера или через SOCKS5-прокси |
| `address` | строка | — | `IP:порт` или `[IPv6]:порт`; только для `socks5` | Адрес SOCKS5-прокси; имена не резолвятся |
| `username`, `password` | строка | пусто | до 255 байт, задаются вместе; только для `socks5` | Вход по логину и паролю (RFC 1929) |
| `interface` | строка | пусто | имя интерфейса до 15 символов | Выходить через интерфейс (`SO_BINDTODEVICE`, без прав на Linux ≥ 5.7). Для `socks5` — соединение до прокси |
| `bind_address` | строка | пусто | числовой IP | Адрес источника для маршрутизации по источнику (`ip rule from …`) |
| `weight` | целое | `1` | 1..65535 | Вес при случайном выборе из нескольких |
| `scopes` | массив или строка `"a,b"` | пусто | имена `[A-Za-z0-9_.-]` до 32 символов | Области; пусто — общая область |
| `enabled` | логическое | `true` | | `false` — запись пропускается |
| `name` | строка | пусто | до 64 символов | Подпись для журнала `watch_ips` и `/v1/config` |

Не больше 32 записей, и хотя бы одна включённая запись должна быть без
`scopes`. Соединения с Telegram и загрузка `getProxyConfig` идут через
апстримы общей области, маскировка — через область `masking_scope`. Апстрим
выбирается случайно по весу для каждого соединения; неудачное ME-соединение
переподключается и выбирает заново. Пароль в `/v1/config` не показывается.

Донор через туннель AWG: Telegram и метаданные идут через SOCKS5 донора, а
локальный сайт-маска — напрямую:

```json
"upstreams": [
  {"name": "donor", "type": "socks5", "address": "10.200.0.1:1080", "weight": 10},
  {"name": "local", "type": "direct", "scopes": "local"}
],
"masking_scope": "local"
```

Свой AWG-интерфейс без SOCKS: соединения уходят через `mtpawg`, а ME получает
внешний адрес выхода туннеля:

```json
"upstreams": [{"type": "direct", "interface": "mtpawg"}],
"me_nat_ip": "198.51.100.20"
```

Маршрутизация подсетей Telegram на уровне хоста (nftables, fwmark,
`ip rule`) работает и без `upstreams`; для ME тогда тоже нужен `me_nat_ip`
с адресом выхода.

## Память и нагрузка

| Параметр | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `workers` | целое | `0` | 0..256 | Число reactors; `0` — по числу доступных ядер с учётом бюджета памяти |
| `cpu_affinity` | логическое | `true` | | Закрепить reactor *i* за *i*-м доступным ядром, если reactors не больше ядер |
| `max_connections` | целое | без лимита | 1..1000000 | Общий предел клиентских соединений |
| `max_handshakes` | целое | без лимита | 1..1000000 | Общий предел одновременных рукопожатий |
| `global_buffer_bytes` | целое | авто | от минимума до 64 ГиБ | Бюджет буферов пересылки, делится поровну между reactors |
| `max_frame_bytes` | целое | `2097152` (2 МиБ) | 4096..16 МиБ | Предел собираемого кадра |
| `connection_queue_bytes` | целое | `262144` (256 КиБ) | 4096..16 МиБ | Очередь одного соединения |

**Бюджет по умолчанию.** Если `global_buffer_bytes` не задан, берётся четверть
памяти, доступной процессу (меньшее из RAM и лимита cgroup, например
`MemoryMax=`), от 64 МиБ до 64 ГиБ; если объём памяти не определяется —
256 МиБ. Выбранное значение пишется в журнал при старте.

**Минимум.** Каждому reactor нужно не меньше
`2 × max_frame_bytes + 2 × connection_queue_bytes + 64 КиБ`. Явно заданное
число `workers` должно помещаться в бюджет, иначе конфигурация отклоняется.
`global_buffer_bytes` ограничивает буферы пересылки, а не весь RSS процесса.
Если задан `max_connections` и бюджета меньше 64 КиБ на соединение, прокси
предупреждает об этом при старте.

Как подобрать значения для тысяч соединений и как понять, что бюджет
исчерпан, — в разделе [Высокая нагрузка](../README.md#высокая-нагрузка)
README.

## Тайм-ауты и соединения клиентов

| Параметр | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `handshake_timeout_seconds` | целое | `15` | 1..120 | Тайм-аут рукопожатия |
| `idle_timeout_seconds` | целое | `1800` | 30..86400 | Тайм-аут простоя соединения. Соединение, которое прокси сам держит на паузе по лимиту скорости, простаивающим не считается |
| `client_keepalive_seconds` | целое | `60` | 0..7200 | TCP keepalive клиентских сокетов: пробы после этой паузы; `0` выключает |
| `client_ack_timeout_seconds` | целое | `90` | 0 или 10..3600 | `TCP_USER_TIMEOUT`: сброс клиента, не подтверждающего данные; `0` — значение ядра |
| `shutdown_timeout_seconds` | целое | `10` | 1..120 | Предел плавного завершения reactor |

Keepalive и `TCP_USER_TIMEOUT` закрывают пропавших мобильных клиентов силами
ядра, а не через `idle_timeout`.

## Шейпинг медиа

Шейпинг ограничивает скорость **медиа-соединений**: соединений с
отрицательным signed DC, по которым клиент Telegram загружает и выгружает
файлы, фото и видео. Сообщения и основные соединения он не трогает. Личные
лимиты пользователя на все соединения (`rate_limit_up_bytes_per_sec`,
`rate_limit_down_bytes_per_sec`) задаются в политике пользователя через API и
действуют независимо; см.
[API.md](API.md#как-применяются-ограничения).

```json
"shaping": {
  "media_download": {"user_kbps": 8000, "total_kbps": 400000, "burst_kib": 4096, "dcs": [-2, -4]},
  "media_upload":   {"user_kbps": 2000}
}
```

Каждое правило включается отдельно. Отсутствующее правило или правило с
нулевыми скоростями ничего не ограничивает.

| Правило | Направление |
| --- | --- |
| `media_download` | Telegram → клиент (загрузки) |
| `media_upload` | Клиент → Telegram (выгрузки) |

| Поле | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `user_kbps` | целое | `0` | 0..100000000 | Лимит на одного пользователя, кбит/с; `0` — нет |
| `total_kbps` | целое | `0` | 0..100000000 | Лимит на весь сервер, кбит/с; `0` — нет |
| `burst_kib` | целое | `0` | 0 или 16..1048576 | Запас, который соединение после паузы передаёт на полной скорости, КиБ. `0` — одна секунда доли, не меньше 64 КиБ |
| `dcs` | массив целых | `[]` | −1..−5 без повторов | Какие медиа-DC затрагивает правило; пусто — все |

Скорости задаются в килобитах в секунду: `8000` — это 8 Мбит/с, или
1 000 000 байт/с.

### Как делится лимит

- **Сначала пользователи, потом соединения.** `total_kbps` делится между
  пользователями, у которых есть активное медиа-соединение этого правила, а
  доля пользователя — между его соединениями. Пользователь с двадцатью
  соединениями получает из общего лимита не больше, чем пользователь с одним.
- **Неиспользованное достаётся соседям.** Раз в секунду каждое соединение с
  лимитом относится к «тяжёлым» (упиралось в свою долю: было остановлено
  лимитом или израсходовало не меньше 90% доли) или к «лёгким». Тяжёлые
  делят то, что оставили лёгкие, но никогда не получают меньше равной доли.
  Так работает на каждом уровне: внутри пользователя и между пользователями.
  Лёгкое соединение, которому понадобилось больше, сначала упирается в равную
  долю, а через секунду становится тяжёлым.
- **Общий бюджет держит лимит при любом числе соединений.** Кроме своей
  доли, каждое соединение списывает трафик с общих бюджетов: пользователя и
  всего правила на сервер. Новое соединение не получает свежий запас, а ждёт,
  пока общий бюджет не выйдет из долга. Поэтому частое открытие коротких
  соединений и параллельные запросы частей файла лимит не обходят.
- **Медиа-запросы оплачиваются заранее.** На маршруте Middle-End каждый
  отправленный медиа-запрос сразу списывает 128 КиБ с общих бюджетов: после
  паузы соединения не отправляют запросы все разом. Ответ сначала расходует
  эту предоплату, неиспользованный остаток возвращается через секунду
  тишины или при закрытии соединения.
- **Активным** считается соединение, передавшее данные за последнюю секунду
  или стоящее на паузе по лимиту.
- **Ничего не отбрасывается.** Перерасход снимает чтение с источника данных,
  данные не теряются и дополнительно не буферизуются. На маршруте Middle-End
  загрузка ограничивается приближённо: общее ME-соединение нельзя
  притормозить ради одного клиента, поэтому останавливается чтение запросов
  клиента, а уже пришедший большой ответ уходит целиком.

### Запас на всплеск

`burst_kib` — главный способ ограничить длинные загрузки, не замедляя
короткие. Прокси не видит содержимого (трафик MTProto зашифрован), поэтому
правило не может отличить видео от фото по типу. Зато короткие передачи (фото,
стикеры, голосовые) укладываются в запас и идут без ограничения, а длинные
(видео, большие файлы) после исчерпания запаса идут со скоростью правила.
Запас пользователя делится между его активными соединениями, но не меньше
16 КиБ на соединение. Запас правила действует, пока медиа-лимит — самое
жёсткое ограничение соединения.

### Личные лимиты пользователя

Поля политики `media_rate_limit_down_bytes_per_sec` и
`media_rate_limit_up_bytes_per_sec` заменяют `user_kbps` правила для одного
пользователя: `null` — как в правиле, `0` — без личного медиа-лимита (общий
`total_kbps` всё равно действует), от 1024 — свой лимит в байтах в секунду.
Подробнее — в [API.md](API.md#пользователи-и-политика).

### Изменение без перезапуска

- **Файл.** `systemctl reload mtdd` применяет новые скорости и `burst_kib` к
  открытым соединениям; изменённый `dcs` — к новым соединениям.
- **API.** `PATCH /v1/shaping` временно подменяет правила, `DELETE` снимает
  подмену, `GET` показывает действующие правила и живые счётчики. Подмена не
  записывается в файл: после перезапуска действуют правила из конфига. См.
  [API.md](API.md#шейпинг-медиа).
- **Лаунчер.** `install.sh shaping` показывает правила и нагрузку,
  `install.sh shaping set ПРАВИЛО ПОЛЕ ЗНАЧЕНИЕ` меняет одно поле через API,
  `install.sh shaping reset` возвращает правила из файла.

### Устаревшие ключи

`media_user_rate_kbps` и `media_total_rate_kbps` на верхнем уровне по-прежнему
принимаются и означают `shaping.media_download.user_kbps` и `total_kbps`.
Вместе с `shaping.media_download` их задавать нельзя: конфигурация будет
отклонена.

### Метрики шейпинга

| Метрика | Значение |
| --- | --- |
| `mtdd_shaping_limit_bytes_per_second{class,scope}` | Действующий лимит правила, байт/с; `scope` — `user` или `total` |
| `mtdd_shaping_burst_bytes{class}` | Запас правила, байт |
| `mtdd_shaping_active_users{class}` | Пользователи с активным медиа-соединением правила |
| `mtdd_shaping_heavy_users{class}` | Пользователи, у которых есть тяжёлое соединение |
| `mtdd_shaping_light_bytes_per_second{class}` | Сколько за последнюю секунду передали лёгкие соединения |
| `mtdd_media_throttled_total`, `mtdd_media_upload_throttled_total` | Сколько раз медиа-соединение останавливалось лимитом (загрузка, выгрузка) |
| `mtdd_user_rate_active_connections{user}` | Активные соединения пользователя с лимитом |
| `mtdd_user_rate_heavy_connections{user,direction}` | Из них тяжёлые |
| `mtdd_user_rate_share_bytes_per_second{user,direction}` | Сколько сейчас может передавать одно тяжёлое соединение пользователя, байт/с; `0` — без лимита |

`class` — `media_download` или `media_upload`, `direction` — `c2s` или `s2c`.
Метрики пользователя выводятся, только пока у него есть активное соединение
с лимитом. Все значения обновляются раз в секунду.

## Наблюдение и подозрительные адреса

| Параметр | Тип | По умолчанию | Допустимо | Назначение |
| --- | --- | --- | --- | --- |
| `watch_ips` | массив строк | `[]` | до 64 IP или CIDR | Подробный журнал каждого этапа соединений с этих адресов (`mtdd watch:`) |
| `fingerprint` | логическое | `false` | | Снимать SYN (`TCP_SAVE_SYN`) и разбирать ClientHello, чтобы определить платформу устройства (Android, Apple, Windows, Linux); без него платформа `Undefined` |
| `suspects` | логическое | `false` | | Учёт подозрительных адресов (`GET /v1/suspects`) |
| `suspect_watch_score` | целое | `60` | 0..100 | Счёт, с которого адрес получает журнал как у `watch_ips`; `0` — никогда |
| `suspect_ban_score` | целое | `0` | 0..100 | Счёт теневого бана: соединения с верным секретом уходят в маскировку; `0` — выключено |
| `suspect_ttl_hours` | целое | `168` | 1..720 | Через сколько часов без событий запись удаляется |

Что пишет журнал `watch_ips`, какие признаки учитываются в счёте и как
работает теневой бан — в разделах README
[Наблюдение за адресами](../README.md#наблюдение-за-адресами) и
[Подозрительные адреса и fraud score](../README.md#подозрительные-адреса-и-fraud-score).
`fingerprint` стоит `getsockopt` и разбора ClientHello на каждое соединение.
